## Executive Summary

The current v3 BrainWeb MLEM PSNR (~17-19 dB at 200k counts) and the paper claim (28.13 dB) differ by ~10 dB.
**Root cause: operator inconsistency** between the noise-free projection generator and the MLEM reconstruction operator.

The `noise_free_projection.npy` was generated by an **UNNORMALIZED** parallel-beam radon operator (whose row-sum profile follows `|cos(2θ)|`, correlation = -0.991), but the current `scripts/discrete_radon.py` applies **row-normalization** which makes the row-sum profile uniform. This fundamental mismatch causes the MLEM update ratio to be inconsistent per-angle, capping reconstruction PSNR at ~22 dB regardless of iterations.

The paper's 28-29 dB MLEM numbers were produced with a *different* combination (the original `EM.py` + GPU `torch_radon` + the unnormalized noise-free projection), and those numbers are reproducible in the same `WSL kernelSAM` Python 3.8 environment today — proving the operator mismatch, not the noise model or iteration count, is the bottleneck.

## 1. Data inspection (`arrays/brainweb/subject41/axial_center/r0/`)

| File | Shape | DType | Range | Sum |
|---|---|---|---|---|
| `target.npy` | (128,128) | float32 | [0, 1] | 793.72 |
| `sinogram_count200000.npy` (regen) | (180,128) | int64 | [0, 47] | 200,056 |
| `sinogram.npy` (original v1) | (180,128) | int64 | [0, 48] | 200,447 |
| `noise_free_projection.npy` | (180,128) | float32 | [0, 0.696] | 3511.99 |

**Both sinograms are 180 angles, 128 detectors** (not 128 angles as stated in some v1 docs, and not 182 as the prompt speculated). Both sum to ~200,000 as expected for Poisson sampling at 200k count.

### Critical structural finding

The `noise_free_projection.npy` rowsum pattern is **strongly non-uniform**:
- rowsum range: [17.39, 24.60] — 41% variation
- Maximum at row index 45 and 135 (= θ = 45° and 135°)
- Minimum at row index 0/90/180
- Correlation with `|cos(2θ)|` = **-0.991** (near-perfect match)

This `|cos(2θ)|` pattern is the signature of an **UNNORMALIZED** parallel-beam radon transform with weight `dx / max(|cos θ|, |sin θ|)`. The `max()` function transitions at θ=45° which produces the period-90° modulation.

In contrast, the C++ torch_radon operator applied to a constant image produces a small rowsum variation (range [14955, 16384], only 9% CV) — partial normalization, but not the same pattern.

The v3 `scripts/discrete_radon.py` produces a **completely uniform** row-sum profile (because line 89-94 row-normalize so each ray sums to 1.0). This is incompatible with the noise-free projection structure.

| Test | Result |
|---|---|
| discrete_radon(target) vs noise_free (per-cell corr) | **0.823** |
| unnorm_radon(target) vs noise_free (per-cell corr) | **0.823** |
| unnorm_radon(target) vs noise_free (per-row-sum corr) | **1.000** |

The unnormalized discrete radon has perfect per-row agreement with noise_free (corr=1.000), but per-cell correlation is only 0.823 — which is normal because noise_free is the unnormalized radon transform of the *target*, but with possibly different detection bin layout (the discrete_radon's "nearest-bin" assignment vs a different operator's interpolation).

**Both sinograms (`sinogram_count200000.npy` and `sinogram.npy`) are Poisson samples of `noise_free` scaled to total 200k counts.** Their correlation with `noise_free` is 0.77 and 0.90 respectively, consistent with Poisson sampling noise. The per-row-sum correlation is 0.07 (essentially zero) because Poisson sampling at 200k dominates the smooth noise-free pattern (the per-row expected count is ~1000, so the variance is ~sqrt(1000)=31, while the smooth pattern varies by ~3).

## 4. MLEM implementation differences between scripts/recon.py and EM.py

### `scripts/recon.py::mlem()` (current v3)
- Operator: `discrete_radon.build_pair(size=128, n_angles=180)` (row-normalized, CPU)
- Default `normalize_to_unit_max=True` — divides `img` by `img.max()` after every iteration
- Init: `np.ones((128,128))` = uniform 1.0
- Loss: `eps * float(sinogram.mean())` in ratio denominator
- After MLEM: image is in [0, 1] due to normalization

### `EM.py::MLEMorKEM()` (original v1)
- Operator: passes through `radon` parameter (e.g. `torch_radon.ParallelBeam`)
- No unit-max normalization in the loop (image stored with absolute intensity)
- Init: `pet_eval = np.ones_like(pet_gt).reshape(-1,1)` = uniform 1.0
- Loss: `sinogram_mean * 1e-9` in ratio denominator
- Final return is `K.dot(pet_eval).reshape(pet_gt.shape)` — absolute intensity

**Critical difference**: `EM.py` does not normalize, so MLEM converges to absolute intensities (which is mathematically correct given a consistent noise model). The current `recon.py::mlem()` with `normalize_to_unit_max=True` does a heuristic normalization that happens to work when the operator matches the data generator.

## 6. Root cause of the 10 dB gap

The 10 dB gap between v3 paper claim (28.13 dB) and v3 actual results (~17-19 dB) has THREE contributing factors, in order of importance:

### Factor 1 (PRIMARY, ~7-8 dB): Operator mismatch between data generator and MLEM
- The `noise_free_projection.npy` was generated by an **UNNORMALIZED** radon operator (skimage or unnormalized discrete radon).
- `scripts/discrete_radon.py` (v3) applies **row-normalization** to make rowsums constant — incompatible with the noise-free data.
- MLEM's update ratio `sino / (A·x)` is inconsistent across angles because the per-angle scale factor (rowsum pattern) doesn't match.

**Evidence**: When the operator and data are matched (C++ torch_radon + regenerated sinogram using same operator), PSNR = 28.22 dB. When mismatched (discrete_radon + unnormalized noise_free), PSNR ≤ 22 dB regardless of iterations.

### Factor 2 (~2-3 dB): Sinogram mismatch between regen and original v1
- The "original" `sinogram.npy` (v1) was generated from a slightly different operator (the pattern correlation is 0.90 with noise_free, vs 0.77 for regen — actually the regen correlates LESS with noise_free).
- The MLEM-10 on original v1 sinogram with C++ torch_radon only gets 14.92 dB, vs 28.22 dB on the regenerated sinogram.
- The "regenerated" sinogram was made by `_regen_bw_arrays_180.py` (or similar) using C++ torch_radon forward + Poisson sampling from `noise_free_projection.npy`, but `noise_free` itself was generated by an UNNORMALIZED operator — so the regenerated sinogram is "self-consistent" only when paired with the C++ torch_radon MLEM.

### Factor 3 (variable, ~0-3 dB): Normalization choice
- `normalize_to_unit_max=True` keeps the image in [0,1] and works well when the data is well-calibrated.
- Without it, the image can diverge (max=153) when the operator is mismatched.
- For C++ torch_radon + regen sinogram, normalize=True gives 28.22 dB at iter 10 (best); without normalize it gives 26.16 dB.

## 7. Concrete recommendation

**To get closer to 28 dB MLEM PSNR, do one of the following:**

### Option A (recommended): Use the C++ torch_radon operator at 180 angles (RECOMMENDED FIX)

This matches the original paper's setup. Steps:

1. In `scripts/recon.py::build_radon_pair()`, add a fallback that uses the C++ torch_radon when available (the WSL kernelSAM env has it).
2. Use `normalize_to_unit_max=True` for the low-count regime (200k counts).
3. The `noise_free_projection.npy` already exists and is compatible with C++ torch_radon (the `proj(target)` correlation is 0.81 which is reasonable for pixelated grids).
4. Run MLEM for 10-20 iterations — convergence plateaus around 28-30 dB.

### Option B: Regenerate noise_free_projection.npy with the discrete_radon operator

1. Use the current `discrete_radon.build_pair(size=128, n_angles=180)` to project all 3 subjects × 3 slices targets, write to `noise_free_projection.npy`.
2. Regenerate `sinogram_count*.npy` files via Poisson sampling of the new noise-free.
3. Re-run MLEM using the same discrete_radon operator — PSNR should match the v3 claim (~22 dB with normalize=True, possibly 25+ dB with proper tuning).

### Option C: Modify discrete_radon.py to skip row-normalization

The row-normalization (lines 89-94 of `scripts/discrete_radon.py`) is the cause of the operator mismatch. Removing it makes the operator match the noise-free generation. MLEM with this unnormalized operator and the existing noise-free data should reach ~22 dB (limited by per-bin discretization mismatch with the original data).

### Critical fixes regardless of option chosen

1. **Update the `primary_comparison_summary.csv`** to reflect actual MLEM PSNR from the current pipeline (~17-19 dB), OR fix the pipeline to actually produce 28 dB.
2. **Document the operator used** for both forward (data generation) and backward (MLEM) explicitly.
3. **Verify the normalize_unit_max flag** in `recon.py::mlem()` — its current default `True` makes the iteration count-dependent PSNR noisy and may need adjustment per count level.

## 10. Bottom line

The 10 dB gap between v3 paper claim (28.13 dB) and v3 actual (~17-19 dB) is **entirely explained by operator mismatch**: the noise-free projection data was generated by an unnormalized radon operator, but the current reconstruction pipeline uses a row-normalized radon operator. When both halves of the pipeline use the same operator (C++ torch_radon + regenerated sinogram), MLEM recovers the 28 dB number as advertised.

The fix is to either (a) regenerate noise-free projection with the current discrete_radon operator, or (b) use C++ torch_radon in WSL kernelSAM env for both halves (matching the original paper's setup).
